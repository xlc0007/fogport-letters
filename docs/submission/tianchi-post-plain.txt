【雾港来信】把 AI 关进规则里：用 Qoder 做一个 4 小时、12 种收束的中文互动叙事

黎明 07:17，旧钟最后一响后，整座雾港都会忘记你。
你只有一封信，和四个小时。

参赛人： 熊诗毅、黄广程 ｜ 团队作品
作品类型： Lifehack
在线体验： https://fogport-letters-e3phwckhb92.qoder.zone
项目仓库： https://github.com/xlc0007/fogport-letters

一、自我介绍

我们是熊诗毅、黄广程。我们想做的不是“和 AI 聊天”，而是一个真正会结束、会记住选择、也会让玩家承担代价的互动故事。

《雾港来信》由我们共同设计，在 Qoder 辅助下完成。它有一个固定的世界、一条必须走完的主线、四位有自己秘密的人物，以及一组由服务端决定的结局。Qwen 负责把这一回合写得可信、有温度；但真相、时间、状态和结局不能由模型随口改写。

我们想验证一件事：当 AI 只负责叙事、不负责规则时，文字冒险能不能既保留自由感，又真正像一个游戏？

这次参赛，我们把项目拆成了三个可以被复用的 lifehack：

1. 把“真相”从提示词里拿出来，交给可测试的服务端规则；
2. 把 AI 的输出压短，让每一回合只推进一件具体的事；
3. 把结局做成条件收束，而不是让模型即兴发挥。

---

二、作品是什么

一句话：你是一名夜班邮差，必须在黎明前找回自己的名字；否则 07:17 的钟声响起后，整座雾港都会忘记你。

游戏从 03:17 开始，到 07:17 结束，共 240 分钟。你要在四个小时里走完五个地点、和四位 NPC 交谈、找到三条关键线索，最后做出选择。

【图 1：主页】

图 1：主页。开始、继续、存档、成就四个入口；每一回合都会自动留下记录。截图使用默认代号「林见雾」，不含任何真实个人信息。

它不是聊天框，而是一条会收束的夜班

- 一条固定主线：查明无名信的寄件人，阻止雾港忘记你。三个关键阶段是停摆的 03:17、白鹭号与林雾、灯塔日志里的旧钟回声。
- 四个有自己秘密的人：老周、何姨、阿礁、温简。每个人有三条可以通过对话了解到的事实，也有一条会随关系和已知事实推进的个人线。
- 四小时真的在走：每回合基础 10 分钟；移动、发现线索、低体力或低意志会额外耗时。07:17 到达时，故事会强制收束。
- 四类结局、十二种收束（含隐藏真结局）：托付对象不同、线索不同、信任不同，结局标题和尾声也会不同；完整调查后还会触发一个隐藏真结局。
- 一张会呼吸的地图：五个地点、雾灯书店、四位人物的实时位置。鼠标悬浮人物头像会放大并打开身份卡；移动端点按查看。
- 主页与存档：开始、继续、存档、成就四个入口；每回合自动存档，主页可以读取本浏览器保存过的不同夜晚。
- 15 枚成就徽记：覆盖读信、线索、信任、探索、存档与结局；隐藏成就不会在解锁前泄露名称。
- 不剧透的结局系统：玩家只能看到已经解锁的最后选择，未解锁结局的名称、描述和条件不会提前出现。

三、为什么做

我们遇到过三种很典型的 AI 文字冒险问题。

第一，聊着聊着就散了。 模型很会接话，但玩家不知道自己该干什么，最后变成“问一句、答一句”，故事没有真正的推进。

第二，模型会忘、会重复、会提前把底牌翻出来。 它可能把已经知道的事再说一遍，也可能为了显得聪明，直接猜中寄件人是谁。对悬疑故事来说，这是致命的。

第三，失败回合很容易变成空转。 玩家等了几十秒，只得到一句“行动没有成功”，既没有线索，也没有时间感，更不知道下一步该做什么。

所以《雾港来信》的设计原则很明确：

1. 真相和规则归服务端。 三条关键线索、时间推进、人物关系、最后选择和结局条件都写在固定故事文件里，模型不能改写。
2. AI 只写这一回合。 Qwen 负责对白、环境和局部后果，叙事要求 80–130 个汉字，服务端硬上限 160 字，避免一回合写成长篇小说。
3. 每次行动都要有可理解的反馈。 要么状态变化，要么时间推进，要么明确告诉玩家“这次没有成功，但时间过去了多久”。
4. 结局不能被提前消费。 未解锁的结局不出现在界面上；玩家走到哪一步，才看到哪一步的选择。

这四条原则不只适用于游戏，也可以直接迁移到 AI 客服、AI 教学和任何“模型不能乱改事实”的场景。

四、怎么用（5 步）

1. 领取邮包，检查无名信。 在主页点「开始」，信封上写着你的名字，纸面浮出一句「别忘了你叫什么」。
2. 选择一条明确的行动。 点击系统给出的建议，或者自己输入行动。建议会指出目的地和预计耗时。
3. 在城市里调查。 去钟楼核对停摆的指针，去旧码头打捞白鹭号的遗物，去北岸灯塔翻阅日志，也可以绕去蔷薇巷的雾灯书店。
4. 和人物建立信任。 老周知道死信去了哪里，何姨守着钟室，阿礁记得那晚的潮水，温简保存着一张旧照片。关系达到 65，人物才会真正信任你。
5. 在 07:17 前做最后的选择。 敲钟、把信托付给某个人，或者登船离开。时间耗尽也可以是一种结局，但不会是一个没有代价的结局。

五、用 Qoder 做出来的过程

01 先划边界：哪些东西不能交给模型

项目一开始，我们就没有把“故事真相”放进提示词。server/src/game/story.ts 保存寄件人、母亲、白鹭号、旧钟和结局的唯一权威；world.ts 保存地点、人物、物品和可学习事实。

模型只能提议白名单内的事件：设置标记、添加物品、调整关系、移动、学习事实。每一条事件都要经过服务端校验，最后在同一个 SQLite 事务里写入。

这层边界让 Qoder 的代码生成有了明确的落点：它不是在“写一个 AI 应用”，而是在实现一套可验证的叙事规则。

02 它先帮我们找到“吞回合”的真因

真正让我们决定重做回合结算的，是一次玩家试玩。

第 6 回合，玩家输入“掀开铁皮柜门查看里面有什么”。等待了 23 秒，页面却提示“候选事件未通过世界规则校验”。回合数从 5 变成 6，但没有物品、线索、位置或关系变化。

排查后发现：模型同时提出了两条事件，一条是重复学习已经知道的事实，另一条是合法的灯塔线索。旧逻辑只要发现任何一条非法事件，就丢掉整批结果，连带把合法线索也吞掉了。

修复后的逻辑分成三层：

- 有合法事件、被拒绝的只是无害重复：保留合法子集，沿用模型叙事；
- 有合法事件、但存在实质性非法事件：保留合法子集，改用服务端生成的部分生效叙事；
- 没有合法事件：进入“雾中插曲”，只推进 10 分钟，并明确告诉玩家线索、行囊、位置和关系没有变化。

这比“再试一次”更重要。玩家可以接受失败，但不能接受自己确认过的进展被悄悄抹掉。

03 让时间真的走：4 小时不是一句文案

游戏里的时间不是一个装饰性的倒计时。

- 起步 03:17，黎明 07:17，严格封顶 240 分钟；
- 每回合基础 10 分钟，移动、发现线索、低体力、低意志会额外加时，单回合最多 25 分钟；
- 时间只在已保存的回合推进，网络错误、超时和 5xx 不会推进时间；
- 07:17 到达时，服务端在保存回合的同一事务里结束这一夜。

有了真实时间，最后的选择才有重量。玩家不是在“看完所有内容后点一个按钮”，而是在有限的时间里决定自己愿意放弃什么。

04 我们否掉了两个“看起来更聪明”的方案

第一个是让模型挑红字高亮。 一开始我们觉得把关键句标红会很方便，但试玩后发现模型会选错重点，甚至把伏笔提前标出来。最后取消了模型挑高亮，让正文保持纯文本，把引导交给固定的排版和左侧信息卡。

第二个是把四种结局的条件全列出来。 这看起来很透明，实际上等于提前剧透。现在主线卡只说明“线索、信任和最后选择会影响收束”，最后选择面板只显示已经解锁的选项；结局名称只在真正发生之后出现。

这两个决定都不是 Qoder 替我们做的最优解，而是试玩之后我们自己否掉的方向。Qoder 帮我们把它们实现、测试和验证，但产品判断仍然要人来负责。

05 把“多”改成“少”

AI 很容易把一回合写得信息过载。这个项目的做法是反过来的：

- 叙事压缩到 80–130 个汉字，最多两段；
- 左侧只保留 8 个图标入口，一次只打开一张信息卡；
- 地图上的人物不是装饰，悬浮可以看身份卡，移动端点按也能打开；
- 新线索和新物品会在对应图标上亮一个红点，打开后清除；
- 正文字号、行高和对比度按“长时间阅读”重新调过，旁边不再堆满所有状态。

我们想让玩家把注意力放在故事上，而不是在界面里找信息。

06 让“这一夜”可以重来：主页、存档与成就

最后一轮迭代，我们补上了三个“游戏应该有”的东西：

- 主页：开始、继续、存档、成就四个入口；
- 自动存档：每回合写入本浏览器，主页可以读取不同夜晚；
- 15 枚成就：读取无名信、集齐三条线索、让四个人信任你、走到任意结局，都有独立徽记；隐藏成就解锁前只显示“隐藏成就”。

07 验收：不只跑起来，还要被截图抓住

最后一轮验收同时做了四件事：

npm run typecheck
npm test          # 86 个服务端测试
npm run build
Playwright: 1440 / 390 / 320 多尺寸截图与交互检查

浏览器脚本检查了地图书店标记、人物身份卡、移动端红点、最后选择面板、已结束存档和剧透防护。比如：

- 一个最后选择解锁时，页面只能出现这一项，不能把另外两个结局的名字带出来；
- 320px 下地图身份卡不能超出视口，最后选择面板不能横向溢出；
- 已有存档在升级后仍能读取，时间和结局不会被重置。

这些检查抓住过真实问题：地图头像太小、移动端卡片越界、锁定结局泄漏、某些面板在切换时滚动位置没有重置。它们不是“锦上添花”的测试，而是这个项目能交付的原因。

六、Qoder Sites 部署：从本地 MVP 到可直接打开

这一版不是只放在本地跑。我们用 Qoder 把整个项目迁到了 Qoder Sites：

- 前端：Vite 构建为静态站点；
- 后端：游戏引擎打包成 Edge Function，提供创建会话、读取会话、提交回合三个接口；
- 数据：Qoder Sites 的 function 数据库保存每个夜晚的 JSON 状态与版本号，用版本号做乐观并发控制；
- 模型：Qwen Key 只放在 Site Settings 的 Secret 中，不进入仓库、不进入聊天记录；
- 降级：没有配置 Key 时，自动使用完整的内置演示叙事，玩家仍然可以从头走到结局。

在线版本目前以演示模式运行：不调用外部 API，故事、线索、时间和结局全部可完整体验。配置 QWEN_API_KEY 后，无需改代码即可切换为 Qwen 实时叙事。

七、原创与合规声明

- 游戏代码、世界观、地点、人物、物品、事件规则、界面与文案由我们设计，在 Qoder 辅助下完成。
- Qwen 仅用于生成回合叙事与对白；不参与真相、时间、关系、结局条件和存档写入。
- 角色立绘由我们提供并用于本作品展示；原始图片经压缩后作为静态资源使用。
- 地图底图使用 Kenney Map Pack（CC0）；界面图标来自 game-icons.net（CC BY 3.0，作者 Lorc / Delapouite）。许可与署名记录保留在项目 README 和素材目录的 License 文件中，不进入游戏界面。
- 项目不包含真实 API Key、第三方小说文本或未授权素材。
- 故事为虚构内容，不影射真实人物或事件；不收集真实姓名、手机号等个人信息，存档仅保存在当前浏览器，在线会话使用随机 ID。
- 演示模式不会伪装成模型输出；没有 Key 时会明确显示「本地演示」。

八、三个可以直接复用的 lifehack

1. 先写“不能变的东西”，再写提示词。 把真相、时间、状态、结局条件放进可测试的代码，模型只负责这一回合的表达。
2. 给 AI 的输出设一个硬上限。 80–130 字、最多两段，让玩家每次只消化一个具体变化；长度约束会反过来逼模型聚焦。
3. 让失败也有信息量。 失败回合至少推进时间，并明确告诉玩家什么没有变；这比让模型“再试一次”更能维持信任。
